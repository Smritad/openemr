1. Introduction & How to Use This Document

This document is the formal system documentation for MatrixCMS, the clinic management system built on the OpenEMR 8.0 core and branded by MatrixBricks. It describes — screen by screen, field by field, and role by role — how the application behaves, what data each screen loads, which buttons trigger which backend processes, and which database tables are affected. It is written to be read end-to-end as a reference manual and dipped into as a lookup for any single screen or permission.

Source of truth: The functional details, real example data, login credentials, facility records, and workflows in this document are derived from the MatrixCMS User Manual and the live application. Backend and database details follow standard OpenEMR architecture; where a detail is inferred from that architecture rather than directly observed, it is prefixed with "Technical note:".

1.1 Who Should Read This

End users & clinic managers

Front-office staff, nurses, and physicians who need to know exactly which screen to open, what to type, and what each button does. Read the screen cards and step lists.

BAs, testers & developers

Analysts mapping requirements, QA writing test cases against field validations and success/error outcomes, and developers tracing a UI action to its backend process and database tables.

2. System Overview & Architecture

MatrixCMS is a single web application that runs an entire clinic's clinical and business operations on one shared database. Clinical operations include patient registration, encounters, SOAP notes, vitals, prescriptions, and lab/procedure results. Business operations include appointment scheduling, the fee sheet, checkout, payments, insurance claims, recalls, reporting, and system administration.

2.1 What the System Does

Clinical operations

  • Patient demographics & charts
  • Encounters, SOAP notes, vitals
  • Prescriptions & drug formulary
  • Procedures, labs & result review
  • Patient education & documents

Business operations

  • Appointment scheduling (Calendar)
  • Fee Sheet, Checkout & payments
  • Billing Manager & insurance claims
  • Recalls & patient communication
  • Reports, facilities & user administration

2.2 One App, Many Roles, Same Database

Every user — administrator, physician, nurse, receptionist, or integration service — logs into the same application against the same database. The system does not run different programs for different staff; instead it shows or hides menus and screens based on the role's permissions, so each person sees a customized view of the same underlying data.

5. Login & Authentication Flow

Every MatrixCMS session begins at the login screen. This screen is the single gateway into the application: it collects credentials, verifies them against the staff account store, builds the user's permission context, and routes the user into the main workspace. The sections below document the screen, the server-side authentication pipeline, the validation messages, the password-reset flow, post-login routing by role, MFA status, logout, and the backing database tables.

At a glance: Login page = interface/login/login.php. After a successful login the user lands in interface/main/tabs/main.php (the tabbed workspace). MatrixCMS authenticates against the users + users_secure tables; permissions are loaded from the ACL (phpGACL) tables.

5.2 Authentication Process (Step by Step)

When the user clicks Login, the credentials are POSTed and the server runs the following pipeline before any application screen is shown:

1Submit — the browser POSTs authUser (username), clearPass (password) and language/facility selections to the authentication handler.
2Lookup user — the server reads the row from users by username, confirming the account exists and is active = 1.
3Load secure record — the matching row in users_secure is fetched (it holds the bcrypt password hash, salt, and the Failed Login Counter).
4Verify hash — the submitted password is checked against the stored bcrypt hash. A mismatch increments the failed-login counter.
5Check account state — verifies the account is not disabled, not expired (Password Expiration date), and not locked (failed-login threshold not exceeded). MFA is checked here if enabled (it is not, in MatrixCMS).
6Create session — a new PHP session is initialised; $_SESSION['authUser'], authUserID, authProvider, site ID and language are stored. The failed-login counter is reset to 0.
7Load ACL / role — the user's group membership and permissions are loaded from the phpGACL tables (gacl_aro / gacl_aco / gacl_axo + groups), determining which menus and actions are visible.
8Audit — the login event is written to the log table (event type login, user, timestamp, source IP).
9Redirect — the browser is sent to interface/main/tabs/main.php, which loads the top menu bar and the role-appropriate workspace.

5.4 Forgot / Reset Password Flow

MatrixCMS uses an admin-driven password reset by default. There is no public "Forgot password" link on the staff login page unless the patient portal e-mail reset is explicitly configured.

Admin-driven reset

Admin > Users > (select user) > Edit
1Log in as administrator (FTS-admin-63).
2Open Admin > Users and click the user to edit (e.g. nurse.jane).
3Type the new password in the Password field, then enter the admin's own password to confirm the change (admin re-check).
4Save. The new bcrypt hash is written to users_secure, the Failed Login Counter is reset, and Password Expiration is recalculated.
5The user logs in with the new password.
Password-expiration prompt: When a user logs in after their Password Expiration date, MatrixCMS forces a change-password screen before the workspace loads. The user supplies the current password and a new password meeting the configured complexity rules.
Self-service e-mail reset: Available only for the Patient Portal and only if the portal + outbound e-mail are configured. Staff accounts always reset through the administrator.

5.6 Multi-Factor Authentication (MFA)

Current state: MFA is OFF for every account in MatrixCMS (the Admin > Users grid shows MFA = no for Dr. Patel, dr.kumar, dr.smith, FTS-admin-63, nurse.jane, oe-system and reception.maya). Login therefore completes with username + password only. 5.7 Logout Flow

Logout

Top-right user icon > Logout

Purpose: End the authenticated session cleanly. From the workspace, the user opens the top-right user/account dropdown and selects Logout.

1User clicks Logout in the top-right account dropdown.
2The action is routed through a hidden logout iframe embedded in main.php, which calls the server logout handler without disturbing the visible page.
3Server destroys the PHP session, clears session cookies, and writes a logout entry to the log table.
4Browser is returned to interface/login/login.php, ready for the next login.
Technical note: Idle sessions also expire automatically based on the timeout global; an expired session forces the relogin notice on the login page. Using a hidden iframe lets the logout fire reliably even when multiple application frames/tabs are open.

20. End-to-End Process Flows & Status Changes

This section narrates the two principal revenue-cycle journeys in MatrixCMS using the real worked example of patient Rohan Mehta (Chart ID P1003), visit 2026-05-28, Encounter #25, provider Dr. Anil Kumar, MD at MatrixCMS Bandra Clinic (POS code 11). The visit produces charges of $300 — CPT4 99213 Office visit established ($225) + CPT4 93000 ECG/EKG ($75) — justified against diagnosis ICD10 I10 Essential hypertension. The patient pays a $40 copay at checkout; the remaining $260 is billed to insurance, which pays $225.

Status vocabulary used below maps directly to OpenEMR encounter and claim states. Open = encounter editable; Signed = note eSigned and locked; Unbilled = charges exist, claim not yet generated; Billed = claim generated/submitted (X12 or HCFA); Paid / Cleared = payment posted and claim closed.

20.1 User Flow — Login → Encounter → Document & Fee Sheet → eSign/Checkout → Billed → Paid

Performed by the clinical and front-desk team. Roles involved: Doctor Reception / Front office Nurse (limited). The journey starts when the patient arrives and ends when money is collected.

1Login. Doctor opens localhost/open_cms/interface/login/login.php and authenticates (e.g. dr.kumar / …, Authorized = yes). The main tabbed UI loads at interface/main/tabs/main.php. Status of the day's work: nothing yet.
2Select patient + create encounter. From Calendar the reception marks Rohan "Arrived", which auto-creates the encounter; or via Patient > Visits > New Encounter. Header changes to Rohan Mehta (P1003) — DOB: 1975-11-08 Age: 50 and the top-right shows Select Encounter (1) ▾. Encounter state: Open.
3Document the visit. Inside the encounter the doctor opens the Clinical dropdown and records the SOAP / Assessment: Hypertension uncontrolled (I10), R/O angina, reason "cardio muscles check". Encounter remains Open (note not yet signed).
4Fee Sheet — add charges. Open the Fee Sheet ("Fee Sheet for Rohan Mehta for Encounter on 2026-05-28"). Add CPT4 99213 ($225) and search/add 93000 ECG ($75). Add diagnosis I10 and use the Justify dropdown to link I10 to each procedure row. Click [+ Add Copay] and enter 40. Save. Charges now total $300, copay -$40, balance $260. Encounter is now Open with Unbilled charges (Charge Coded = yes).
5eSign the note. On the Visit Summary the doctor clicks [eSign]. The note is locked (🔒) and the eSign Log records smrita · Anil Kumar MD · 2026-05-28. Encounter state → Signed / Locked. Per the manual, "Locked = billed": once signed the encounter is ready for checkout and is no longer freely editable.
6Checkout & collect copay. Front desk goes Fees > Checkout (or Patient > pos checkout). The Accept Payment screen pre-fills the $40 copay; click Generate Invoice. The encounter is now checked out / LOCKED. Status: Signed + copay collected. Remaining balance $260 is Unbilled.
7Print receipt. Receipt shows the patient's name/address, charges $300, payment -$40, and Balance Due $40 on the patient-responsibility line (with $260 routed to insurer). Patient leaves. Front-desk portion (steps 1-7) is complete.
8Submit the claim (Billed). The biller goes Fees > Billing Manager, filters Date of Service = Today + Billing Status = Unbilled, clicks [Update List]. Rohan appears with balance $260 and status Unbilled. Select the row → [X12 OPTIONS ▾] > Generate X12 (file e.g. claims_20260528_001.x12) or [HCFA FORM] > CMS-1500 for paper. Claim state → Billed / Submitted.
9Payment posting (Paid). ~14 days later Aetna's $225 cheque arrives. Biller uses Fees > Batch Payments to record the deposit and EOB Posting to apply it to Encounter #25. Balance reduces. Claim state → Paid. (See 20.2 for the admin closure step.)

20.2 Admin/Biller Review Flow — Login → Review → Approve/Reject → Closure

Performed by the Admin or authorized billing manager (Reception / Front office with billing rights). This flow controls whether a claim is closed clean or sent back for correction.

1Admin login. admin / pass (or FTS-admin-63, Authorized = yes) at the login screen; the full menu including Admin and Reports is available.
2Review in Billing Manager. Fees > Billing Manager. Build a filter (e.g. Billing Status, Authorization Status, Charge Coded, User, Date of Service, Encounter) and click [Update List]. The 3-panel screen lists each claim with patient, encounter, provider, balance and status. Use View Log / Tab Log to inspect the audit trail (who clicked what, when).
3aApprove path — Mark as Cleared. After the EOB is posted (Aetna $225 applied to Rohan), select the claim row and click [⬇ Mark as Cleared]. The claim is recorded as paid and removed from the outstanding queue. Claim state → Cleared / Closed.
3bReject path — Re-Open. If the claim was denied or a code was wrong, select the row and click [↩ Re-Open] (use sparingly). This re-opens the Signed encounter back to Open so codes can be corrected. Warning: Re-Open voids the claim status — you must re-justify, re-checkout and re-submit X12. On the Fee Sheet the equivalent end-user action is ↩ Void Checkout & Re-Open after the "This encounter has been billed." banner.
4Closure / reconciliation. Once cleared, run View Printable Report with the End Of Day Report - Totals checkbox for daily cash reconciliation (Total Charges / Payments / Adjustments / Balance Due). When Billing Manager > Update List returns no claims for the filter, the revenue cycle for that day is complete.
Do not Re-Open a claim that is already paid (creates an accounting mess), and do not forget to Mark as Cleared after posting (clutters the queue). Clear Log is destructive and admin-only — it permanently erases the HIPAA audit trail.
